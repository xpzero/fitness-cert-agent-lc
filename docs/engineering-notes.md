## 一、当日实录

### 1. GitHub API 间歇性 EOF

- **现象**：`gh search repos` 偶发 `Get "https://api.github.com/...": EOF`，同一命令几秒后重试即成功；一轮调研 20+ 次查询里出现约 6 次。
- **定位**：错误发生在 TLS 握手层而不是 HTTP 语义层（EOF 而非 403/422），且同参重试必成功 → 排除查询语法问题，判定为网络/网关瞬时抖动，与查询内容无关。
- **解法**：查询失败后 `sleep 3` 重试一次即可；批量查询间加 1–2 秒间隔。
- **预防**：对外部 API 默认"会偶发失败"，写带退避的重试是基线而不是可选项；区分"重试能解决的"（瞬时网络）与"重试不能解决的"（鉴权、配额）——看错误发生在哪一层。

### 2. 同一 CLI 不同子命令的字段名不一致

- **现象**：`gh repo view --json stargazersCount` 报 `Unknown JSON field`。
- **定位**：`gh search repos` 走 REST Search API（字段 `stargazersCount`），`gh repo view` 走 GraphQL（字段 `stargazerCount`，没有 s）；`fullName` vs `nameWithOwner` 同理。同一工具的两条子命令背后是两套 API 的命名体系。
- **解法**：直接看报错附带的 available fields 列表（gh 会打印），按它选字段。
- **预防**：不要靠记忆 API 字段——优先用工具的自描述能力（`--help`、报错提示）。同理适用于 OpenAPI、数据库 schema 的多入口。

### 3. 并行子代理触发并发上限

- **现象**：三个研究代理同时启动，两个立刻报 `user concurrency limit exceeded`。
- **定位**：失败不是任务本身的问题，而是运行环境对**同时运行的代理数**有额度限制；三个任务彼此独立，串行不损失正确性。
- **解法**：改为串行派发，逐个等待；期间主线程不空转。
- **预防**：并行化设计前先确认运行环境的并发额度（API 限流、代理数、连接池）。把任务分为"天然并行、值得排队"和"其实串行更省心"两类——并行收益要减去调度成本。

### 4. `str.maketrans` 的键类型陷阱

- **现象**：全角→半角转换 `str.maketrans({c: chr(c-0xFEE0) for c in range(0xFF01, 0xFF5F)})` 抛 `TypeError: ord() expected string of length 1, but int found`。
- **定位**：maketrans 的 dict 形式要求键是**单字符字符串**（内部对键调用 `ord()`），直觉里"码点整数也可以当键"是错的——int 键只在三参元组形式里另有含义（映射到 None）。
- **解法**：`{chr(c): chr(c - 0xFEE0) for c in range(...)}`。
- **预防**：这类"纯函数小工具"最容易裸奔上线——这个 bug 是单测在 1 秒内抓到的。字符处理代码的测试成本几乎为零，没理由不写。

### 5. 中文答案归一化的脏输入细节

- **现象**：判分模块三个测试失败：`"a" ≠ "A"`（单字母没统一大写）、`"C,A" ≠ "A C"`（逗号没清）、`"A、B"` 保留顿号。
- **定位**：初版归一化只覆盖了"全角转半角 + 去空白 + 多字母才大写"，漏了两个现实：考生真的会输 `Ａ、Ｂ ` 这种混合脏输入；单选答案也是字母，大小写规则不该只作用于多选。
- **解法**：归一化规则重写为——全角→半角 → 去空白 → 去中文分隔符（`、，,；;｜|`）→ 纯字母时统一大写（多选拍序，单选直接大写）；"对/错"等中文答案保持原样参与精确匹配。
- **预防**：归一化函数位于"输入不可控"边界上，**必须**用真实脏输入写用例，而不是用自己生成的干净数据测自己。另一条经验：归一化要激进（宁可多清一点），判分逻辑保持纯确定性——脏数据挡在门口，比散落在判定逻辑里好修。

### 6. 扫描版 PDF 的假象文字层

- **现象**：官方 54 页手册用 pymupdf 提取只有 1287 字，且每页都是同一句"国家体育总局人力资源开发中心"。
- **定位**：每页只有页眉有文字层，正文是整页扫描图。教训是"PDF 提取出了文字" ≠ "正文是文本"——1287/54 ≈ 24 字/页这个数字本身就是诊断结论。
- **解法**：OCR 三条路对比后选型——PaddleOCR（中文最准但 paddle 依赖数百 MB）、RapidOCR（onnx 中庸路线）、**macOS Vision**（本机框架、零模型下载、原生支持 zh-Hans）→ 单机工具链选 Vision + pyobjc，54 页 3 万字一次跑通。
- **预防**：拿到 PDF 先算"每页平均字符数"这种廉价指标，再决定走文本提取还是 OCR——把数据形态检查放在管线最前面，下游才不会莫名失败。

### 7. Objective-C 桥接库的 API 与 Swift 文档不一致

- **现象**：`pdf.pages()` 抛 `AttributeError: 'PDFDocument' object has no attribute 'pages'`——Swift 里这是标准属性。
- **定位**：pyobjc 暴露的是 `pageCount()` / `pageAtIndex_(i)` 选择器风格方法；顺带发现 NSImage `lockFocus` 的绘制路径在新 macOS 上已弃用。
- **解法**：改用 `pageCount + pageAtIndex_`，渲染改走 `page.thumbnailOfSize_forBox_(size, box)`，代码还缩短了一半。
- **预防**：用桥接库时**不要照抄原生语言文档**，在 REPL 里 `dir()` 探测实际暴露面；弃用警告（DeprecationWarning）在脚本里要认真看，它们预告的是"下一次系统升级就坏"。

### 8. Vision OCR 的坐标系与中文参数

- **现象**：初版 OCR 输出文本顺序颠倒。
- **定位**：`VNRecognizedText.boundingBox` 的原点在**左下角、y 轴向上**，与图像直觉（左上、y 向下）相反；不排序时结果按识别内部序输出，阅读顺序混乱。
- **解法**：结果按 `-y` 排序；`setRecognitionLanguages_(["zh-Hans"])` + `setUsesLanguageCorrection_(True)` 提升中文连贯性；每页 OCR 后记录字数（3 万字/54 页 ≈ 560 字/页，量级合理）作为质量 sanity check。
- **预防**：任何返回空间数据的 API（OCR、目标检测、版面分析）都要显式处理坐标系；对"感知类"输出（OCR/ASR）加一条便宜的统计校验（字数/页、空页率），能在接入下游前暴露质量问题。

### 9. B站字幕的三层可获得性

- **现象**：字幕抓取脚本 API 链路全部正常（分P列表、播放器接口），但两个国职课程视频都返回"无字幕"。
- **定位**：B站字幕有三层——UP 主上传的 CC 字幕（无需登录）、AI 生成字幕（**需要 SESSDATA 登录态**）、根本没有。实测的 UP 主都没传 CC。脚本没坏，是内容的可获得性分层。
- **解法**：脚本按"CC 优先、AI 兜底"排序选字幕轨；支持 `BILI_SESSDATA` 环境变量注入登录态；拿不到时输出结构化的 skip 信息（而不是报错退出），主流程继续。
- **预防**：爬公开数据前先搞清**内容的可获得性分层**（完全公开 / 需凭据 / 不存在），把"需要用户提供的凭据"设计成可选注入项——依赖分层的缺失应当降级，不应阻塞主流程。

### 10. PEP 668 与包管理的边界

- **现象**：`pip3 install pymupdf` 被拒：`externally-managed-environment`；随后 venv 里下载 wheel 时又遇到 SSL EOF 重试。
- **定位**：Homebrew Python 受 PEP 668 保护，系统解释器禁 pip 直装——这是保护不是故障。
- **解法**：项目内建 `.venv`，一切依赖装进 venv，`pyproject.toml` 锁清单。
- **预防**：Python 项目第一天就建 venv 是零成本习惯；把"是否需要全局工具"与"项目依赖"分开，永远不要为了一个包污染系统解释器。

### 11. JS 渲染站点：换"抓正文"为"搜直链"

- **现象**：官网首页找不到"考核实施细则"；测评平台是纯 JS 应用，抓不到正文；通知公告栏目有 52 页列表。
- **定位**：政府/SPA 站点的重要文件通常不在导航上，而是散落在历史通知的**附件**里；对 JS 渲染页做 DOM 抓取消耗大、收益低。
- **解法**：搜索引擎 `site:` 限定 → 定位到含关键词的通知 → 从通知页拿附件直链（`ceping.sportosta.org.cn/nlcp/download/gzsc.pdf`），54 页官方手册一步到位。
- **预防**：抓取 JS 重度站点前，先花 2 分钟试搜索引擎的间接路径——很多"抓不到"其实是"不值得抓"。对政府站点尤其如此：**通知公告是信息的主索引**。

### 12. 秘钥的搬运与最小暴露面

- **现象**：需要复用本地 opencode 配置里的智谱 API key 到新项目。
- **解法**：脚本从 `auth.json` 直写 `.env`（管道内完成，不在终端回显明文）；对话与日志里一律掩码展示；项目创建当天 `.env` 先于任何提交进 `.gitignore`（并配合 `knowledge/raw/` 的版权材料目录一起排除）。
- **预防**：秘钥卫生三条——搬运用代码不用复制粘贴（避免进 shell history）、展示必掩码、gitignore 前置。同理处理版权材料：语料仓库从第一天起分 `raw/`（排除）与 `processed/`（结构化、带来源）。

## 二、泛化：LLM Agent 开发的经典问题模式

把上面 12 条实录收敛成 8 个可复用的模式（每个标注来源实录编号）：

### P1 外部调用的韧性（← 实录 1/2/10）

任何跨进程边界（HTTP API、CLI、模型服务）的调用都默认会偶发失败。工程动作：带退避的重试、按错误层级分类（可重试 vs 不可重试）、限速礼貌、以及**用工具的自描述接口代替记忆字段名**。

### P2 输入不可控边界的归一化（← 实录 4/5）

Agent 的输入来自真人、模型输出也是"脏数据"。原则：归一化+校验发生在进入确定性逻辑**之前**，且用真实脏输入写测试。本项目里对应答案判分，同样的模式适用于工具调用的参数清洗、用户表单、OCR 文本。

### P3 数据可得性先行（← 实录 6/9/11）

写管线代码之前，先验证语料"能不能拿到、是什么形态"（文字层还是扫描件、CC 还是 AI 字幕、免费还是需凭据）。形态检查用最便宜的指标（字符数/页、空页率）做哨兵，把"数据不符合预期"挡在管线入口，而不是让它在第 N 层莫名失败。

### P4 防幻觉是 schema 设计，不是 prompt 技巧（← 设计决策）

本项目把"可溯源"做进数据模型：chunk 带 `page_no`、题目带 `evidence_text`（从原文逐字定位）、回答带 `[chunk:ID]` 引用 + NLI 校验、检索质量不达标走拒答分支。**拒答和拒绝入库是特性不是缺陷**——验收指标（引用正确率 ≥0.95、出题抽检 ≥0.97）与 CI 门槛绑定。

### P5 确定性与 LLM 的分工（← 设计决策）

能确定性解决的不用 LLM：客观题判分零模型调用；路由/自检/评分用小模型；只有生成（出题/讲解）用大模型。收益是成本、延迟、可复现性三者同时改善。反模式：拿大模型做字符串比较。

### P6 评测驱动开发（← 设计决策）

金标准集（jsonl 进 git）+ 每指标门槛 + CI 回归，先于功能完备。最小集：检索 recall@k、引用正确率、拒答准确率。判据：**任何 prompt/检索参数改动必须过评测门槛**，否则不允许合并——这让"改一下提示词"从玄学变成工程。

### P7 凭据与敏感内容的最小暴露面（← 实录 9/12）

需要用户凭据的外部依赖，凭据一律做成可选注入（环境变量），缺失时降级不阻塞；敏感文件（秘钥、版权语料）在仓库创建当天就划出边界（gitignore），不事后补救。

### P8 运行环境的额度意识（← 实录 3/8）

并发额度、API 限流、坐标系/坐标系转换这类"环境约定"，都属于**在架构设计前要确认的约束**。并发设计要先问"环境允许几个"；空间/时序数据要先问"坐标原点在哪"。这两类错误的特点是：代码完全正确，只在特定环境下才炸。

# Day 1 续：P1 启动日新增实录（RAG 链路）

### 13. API key 的"模型配额矩阵"比连通性更重要

- **现象**：chat 端点 OK，embedding 端点持续 429；换模型 glm-4.6 报 429/1113"余额不足"；glm-4.7 返回 200 但 content 为空。
- **定位**：这把 coding-plan key 不是"能不能调通"的问题，而是**逐模型的配额矩阵**——embedding 无配额、4.5-air/4.6/4.5 无 bigmodel 配额、glm-4.7 是思考模型（content 被 reasoning 占满，需读 reasoning_content 字段）。同一个"429"背后有三种不同语义。
- **解法**：写探测脚本一次跑完 base × model 矩阵，按"角色 × 可用模型"定映射（生成 glm-4.5-air @ z.ai、轻任务 glm-4.5-flash @ bigmodel），llm.py 按角色支持不同 base_url。
- **预防**：接第三方模型服务先跑探测矩阵再写代码；错误处理区分"可重试瞬时错误"（SSL EOF）与"语义明确快失败"（1113 无配额）。

### 14. create_all 不做迁移——表结构与代码漂移

- **现象**：检索 SQL 报 `column "authority_level" does not exist`，但表定义里明明有。
- **定位**：表在旧版模型时已创建，`Base.metadata.create_all` 只建缺表、不改已有表；旧 chunks 表没有后来加的列。真正原因是我的检索 SQL 本身写错了表（authority_level 在 documents 不在 chunks）——两个问题叠加。
- **解法**：清库重建（语料可再生，重建零成本）；SQL 修正为 JOIN documents。
- **预防**：原型期用"可再生气ited数据库"（删了重来）代替迁移；写 JOIN 前先 \d 表结构确认列在哪个表。

### 15. 先诊断纯通道，再动融合权重

- **现象**：混合检索 Recall 低，权威级加权（1.3/1.1/0.8）被怀疑压住了正确结果。
- **定位**：先跑**纯 dense** 排序看理想 chunk 排第几——发现纯 dense 是对的（RICE chunk 排第 2），是 RRF 等权融合 + 强权威加权把它拉下去；且语料里根本不存在某查询的理想 chunk（"卧推→胸大肌"只有动作名称列表，无语义段落）。
- **解法**：权威权重降为平局打破（1.05/1.0/0.95）；dense 0.65 / sparse 0.35 加权 RRF；稀疏通道 `similarity()` 换 `word_similarity()`（短查询 vs 长文档）；双路 dense（原始 + HyDE）取最优秩。Recall@5：0.641 → 0.718 → 0.821。
- **预防**：调融合参数前必须先看各通道独立排序（"先诊断纯通道"）；**对不存在的 ground truth 调参是徒劳的**——先确认理想答案在语料里，再谈排序。

### 16. 自动金标准的两个坑：相关集不完整与元信息 chunk

- **现象**：评测 miss 里一半是"检索到的碎片其实含答案但不在金标准相关集"；另一个 chunk"元信息"（来源清单表）总排第一。
- **定位**：OCR 表格语料同一规则散布多页碎片，单一 relevant chunk 不公平——用 embedding 近似（cosine ≥0.80）把等价碎片并入相关集；元信息 chunk 语义上真含关键词（来源清单里提到 RICE），属于"非知识内容混入语料"。
- **解法**：摄取端支持 `start_marker` 跳过元信息前缀；评测端相关集扩展。
- **预防**：摄取管线要识别"结构性前缀"（目录/元信息/版权页）；自动金标准的天生缺陷（相关性不完整）要在评测脚本里补偿，并在报告里声明这是 auto 集不是人工集。

### 17. 词面校验被 markdown 污染

- **现象**：引用支撑度抽查把正确答案判 0/4——但答案确实来自所引 chunk。
- **定位**：LLM 输出带 `**加粗**`、`- 列表`、`①` 等 markdown 装饰，2-gram 统计被装饰符稀释；纯标题行（"二、动作要求"，4 字）也被当论断校验。
- **解法**：bigram 清洗改为只保留 `\w`（CJK/字母/数字）；短于 8 字的结构行跳过抽查。
- **预防**：对 LLM 输出做文本统计前，先做 markdown 剥离——这是"输入不可控边界"（P2 模式）的镜像问题：**输出同样是不可控输入**。

### 18. 第一个真实用户 bug：URL 里的中文（用户实测发现）

- **现象**：用户在界面点"查询官方入口"，报 `UnicodeEncodeError: 'ascii' codec can't encode characters`。
- **定位**：查询参数直接拼接 `?kind=证书查询`——URL 规范只允许 ASCII，urllib 在发送时才对非 ASCII 字符抛错。开发期我用英文参数测试（`kind=cert`），第一个真实用户一点中文按钮就炸。
- **解法**：`urllib.parse.urlencode({'kind': kind})` 做标准百分号编码。
- **预防**：这是"输入不可控边界"（P2 模式）的又一次现身：**凡是拼进 URL/查询的变量，编码必须在边界处完成**。更贵的教训是测试数据的选择——自测时用的永远是干净英文参数，而真实用户的第一下点击就是中文。

### 19. 502 的真凶：系统代理劫持 localhost（用户实测发现）

- **现象**：用户对话报 `HTTP Error 502: Bad Gateway`——但 API 明明在跑。
- **定位**：macOS 上 urllib 默认读取**系统代理**设置（Clash/Surge 等），把发往 `127.0.0.1:8765` 的请求也转发给代理进程；代理无法回连用户本机端口，返回 502。我此前的测试没暴露，因为测试进程没有代理环境——curl 默认不读系统代理，urllib 读。
- **解法**：前端对 localhost 的调用统一用 `build_opener(ProxyHandler({}))` 显式直连；并用"强制走死代理"的环境复现验证（旧方式失败、新方式成功）。
- **预防**：**"我这边测试通过"≠"用户环境没问题"**。代理、locale、PATH 是"开发机 OK、用户机炸"的三大经典来源。调本机服务一律显式绕过代理，别依赖环境恰好干净。

### 20. 超时的三层拆解：客户端余量、链路冗余、错误伪装

- **现象**：用户对话报 `timed out`。实测单次问答 26–60s，波动大。
- **定位**：①客户端 60s 超时，而"校验失败自动重跑第二轮"的最坏路径正好超过 60s；②逐节点计时发现"快模型" grade 调用要 9–11s（与 generate 同量级，且与 verify 的校验功能重叠）；③更隐蔽的——generate 网络出错时，错误文本被 refuse 节点覆盖成"无法溯源"话术，**把服务故障伪装成了知识不足**。
- **解法**：客户端超时 240s；链路减负——grade 改无 LLM 启发式（候选空才拒绝，正确性交给 generate+verify 双闸）、第二轮跳过改写 LLM 与 HyDE、生成上下文 8×600→6×500 字符 + max_tokens 上限；新增 error_out 分支让生成错误透传到用户。
- **预防**：性能问题先**逐节点计时**再动手（guess 型优化最容易砍错地方）；错误处理要审查"错误会不会被下游节点改写"——一个统一的失败话术若不加区分地覆盖一切错误，会把基础设施故障隐藏成产品缺陷。

### 21. 误杀与快模型：词面校验的正确打开方式（用户实测发现）

- **现象**：用户问"三角肌是什么？"被拒答——但这恰是语料覆盖的基础解剖。
- **定位**：生成答案正确且引用正确，卡在 verify：答案是"合理归纳句"（"三角肌是人体的主要肌肉之一"），而引用的 chunk 是 OCR 目录式碎片（标题清单），**没有逐字对应的原文句子**，词面 2-gram 全灭（0/3、0/4）→ 两轮重试全灭 → 拒答。另一个发现：同为"快模型"，glm-4.5-flash 单次 4.5s、glm-4-flash-250414 只要 0.5s——**同端点的不同版本差 9 倍延迟**。
- **解法**：①verify 加两级仲裁——词面快筛不过关的句子，合并成**一次批量**语义蕴含判定（NLI-lite：语义一致即支持，不要求逐字；逐句调用的 60s 也顺便消灭）；fast 模型切到 glm-4-flash-250414。修复后 10–23s 单轮收敛，误杀消失。保留的价值：真引用错位（把"肩外展主作肌"算到"肌肉收缩形式"chunk 头上）仍会被 NLI 正确拒绝——严格性没有丢，只是不再误杀归纳句。
- **预防**：①校验器要区分"逐字复述型语料"与"归纳型回答"——对目录/大纲类语料，词面校验天然高误杀，必须配语义仲裁；②"快模型"是相对概念，**选型以实测延迟为准**（同一家同一端点不同版本差 9 倍）；③同类多次 LLM 调用优先合并为单次批量。

### 22. 端口撞车三部曲与 SQLAlchemy text() 的 ::cast 陷阱

- **现象一**：`make api` 起不来——8000（其他项目）、5432（本机 Postgres）、8765（用户另一个学习项目的 uvicorn）接连被占，且对方的 404/报错会被当成"我们的服务出问题"，极具迷惑性。
- **解法**：端口迁移到 8770；判断"这是谁的服务"的方法——`curl /healthz` 返回的是我们的 JSON 还是别人的 traceback，一眼定位。
- **现象二**：出题入库 INSERT 报语法错误——SQLAlchemy `text()` 里 `:param::jsonb`，`::` 类型转换与命名参数解析冲突（部分参数变成了字面 `:name`）。
- **解法**：改用 `CAST(:param AS jsonb)`。
- **预防**：①本机多项目开发，端口是稀缺资源——服务端口选偏冷号并在 Makefile/前端/文档三处同步；②SQLAlchemy text() 里做 JSONB 转换一律用 CAST 写法；③出题闸门链实测有效：2 题 grounding=1.0 入库、1 题解析失败被拒、1 题质量分 3.0 被闸——**拒绝路径和接受路径一样重要，都要测**。

### 23. 连接池耗尽：靠 GC 归还连接是赌运气（后台长任务暴露）

- **现象**：批量出题脚本跑到中途死掉——`QueuePool limit of size 5 overflow 10 reached, connection timed out`。
- **定位**：大量 `engine.connect().execute(...).all()` 这种"临时连接"写法依赖 CPython 引用计数即时归还连接；但 LangGraph 节点跑在重试包装和异常处理里，**traceback 持有帧引用形成引用环**，GC 被推迟，连接迟迟不回池。短命请求碰运气没炸，长任务几十轮后必然耗尽。
- **解法**：全部 12 处改为 `with engine.connect() as conn:` 显式上下文管理；`create_engine` 加大池余量（pool_size=10, max_overflow=20）双保险。
- **预防**：①资源获取一律上下文管理，**"表达式结束就会回收"在异常和框架包装下不可靠**；②后台长任务是资源泄漏的照妖镜——CI 里跑不满几十轮的短测试永远测不出这类问题，上线前要用"规模化冒烟"（连续跑 N 轮）压一遍。

### 24. 表单参数的隐形降级与启动期 schema 迁移（M1 实录）

- **现象一**：上传接口的 `authority` 表单字段永远存成默认值 3。
- **定位**：FastAPI 里非文件参数不标 `Form()` 时按**查询参数**绑定——multipart 里的表单字段根本没被读。参数"有默认值"掩盖了绑定失败，接口不报错、行为悄悄错。
- **解法**：`authority: int = Form(3)`。**预防**：multipart 端点的每个表单字段都必须显式 `Form()`；给"有合理默认值的参数"写绑定测试（传非默认值断言落库），否则默认值会替你掩盖 bug。
- **现象二**：新加的 `documents.status` 列在 API 进程里不存在——`create_all` 不迁移已存表，ALTER 语句写在 `init_db`，但 API 从未调用它。
- **解法**：schema 初始化挂到 FastAPI startup 事件（幂等 ALTER + create_all）。
- **预防**：任何 schema 变更后，E2E 必须走"新起进程"验证（进程内旧连接/已初始化状态会掩盖迁移缺失）；原型期"删表重建"省事，但一旦有了生产数据就要转幂等迁移。

### 25. 两个"看起来是 bug 其实是协议约束"的 LLM 端点问题（三页改版实录）

- **现象一**：追问接口稳定报 1214"messages 参数非法"，但几分钟前同格式调用成功。
- **定位**：二分定位到与提示词内容无关——**messages 数组只有 system 没有 user 消息**时智谱端点直接拒绝。之前成功的调用都恰好带 user 消息，"内容相关"是错觉。
- **解法**：system 放角色规则，对话记录和指令放 user 消息。
- **现象二**：陪练评估 JSON 解析随机失败——抓原始返回发现 glm-4.5-air 对复杂提示词会**无视 response_format=json_object**，输出英文思考过程（恰好在 2000 字符截断，一个 `{` 都没有）；简单提示词则"恰好"遵守——遵守与否不稳定。
- **解法**：结构性 JSON 任务（评分/判定）全部切到 fast 模型（glm-4-flash-250414，JSON 一直稳定且 0.5s 级）；air 只留给长文本生成。
- **预防**：①"间歇性参数错误"先怀疑协议约束（消息角色构成、字段顺序），用最小用例二分，别只盯着提示词内容；②**response_format 是请求不是保证**——LLM 端点的 JSON 约束要按"尽力而为"对待，解析层必须兜底，关键结构化任务选实测守规矩的模型；③调试 LLM 问题必须抓原始返回——"解析失败"四个字背后可能是超时、截断、思考模式三种完全不同的病。

### 26. Chrome 启发式缓存：强刷也救不回来（用户实测发现）

- **现象**：表格修复已推送，用户 Chrome 里"还是旧页面"，普通刷新无效。
- **定位**：FastAPI StaticFiles 不发 `Cache-Control` 头 → Chrome 启发式缓存旧 `app.js`；我验证用的浏览器上下文无缓存，故"我这边是好的"。
- **解法**：①`/ui` `/next` 响应统一 `Cache-Control: no-store`；②资源引用加版本参数 `app.js?v=时间戳` + 页面右上角 build 角标（肉眼可验证版本）。
- **预防**：版本化 URL 是绕缓存的唯一可靠手段——`no-store` 只管未来响应，管不了已落盘的缓存；"我这边好的"永远要意识到测试环境与用户环境的差异（同 #19）。

### 27. 补丁手术的复制灾难：知识库内容 ×4（用户实测发现）

- **现象**：用户报"知识库里内容重复"——每份文档渲染 12 处、文档列表出现 4 次。
- **定位**：三轮 `str.replace` 补丁在同一文件累积，"表格+双面板"整块被复制 4 份；且其中一份缺收尾括号导致构建失败，修括号时又复制了一份。
- **解法**：放弃外科手术，**整页重写**为单份干净实现（467→122 行净变化）。
- **预防**：对同一文件的字符串替换补丁超过两轮，直接整文件重写——补丁的隐性成本是"你不知道现在文件里有几份"；提交前 grep 关键标记计数（如 `docs.map` 出现次数）可提前暴露。

### 28. 词面检索的空反馈：0 命中时"点了没反应"（用户实测发现）

- **现象**：词面模式搜"坐姿体前屈的合格标准"，点击检索毫无动静。
- **定位**：两层叠加——①`word_similarity` 对口语长查询最高 0.455 < 固定阈值 0.5，后端整级空手而归；②前端对空数组什么都不渲染。用户无法区分"没结果"和"按钮坏了"。
- **解法**：后端阈值分级回退（0.5→0.35→0.2）；前端加"检索中…"按钮态 + 明确的零结果提示（"词面模式无命中——建议切混合/语义"）。
- **预防**：**任何搜索功能必须有三个状态：加载中、有结果、零结果**——零结果不是边界 case，是口语查询下的常态；阈值不该拍脑袋定死，分级回退让"严格优先、宽松兜底"。

### 29. make 目标的两个入门坑（用户实测发现）

- **现象**：①`make api` 报 `uvicorn: No such file or directory`；②`make api && make web` 后页面打不开。
- **定位**：①Makefile 用裸命令名，uvicorn 在 venv 里不在 PATH；②`&&` 语义是"前一命令**退出后**执行"，前台服务永不退出 → 第二条永远轮不到。
- **解法**：Makefile 统一 `.venv/bin/` 绝对路径；新增 `make serve`（后台起 API + 前台起 Web，trap 一次性退出）。
- **预防**：Makefile 里的命令按"干净 shell 新 clone 的机器"标准写；提供一键复合目标，别让用户自己拼启动命令。

### 30. 动作库卡片污染检索域 + HNSW 过滤后置空集（检索评测发现）

- **现象**：RepDB 609 张动作卡入库后，本地检索评测 Recall@5 从门槛之上跌到 0.500；口语问题（"练哪瘦哪能局部减脂吗"）dense 通道前 5 全是卷腹动作卡，开着 HyDE 也救不回。CI 却依旧绿灯。
- **定位**：两层叠加——①动作名碎片（626/1397 = 45% 语料）在 dense 空间与口语查询强近邻，霸占候选；②CI 的 `scripts/ingest.py` 只摄取教材语料，金标准也建于该状态——**CI 语料与金标准配套所以绿，本地语料已漂移**。修复①时又踩出第二坑：给检索 SQL 加 `WHERE d.searchable` 后，部分查询返回 0 行——HNSW 索引**先取候选再过 WHERE**，默认 ef_search=40 的候选池被过滤耗尽（pgvector 过滤检索的经典后置空集问题）。
- **解法**：documents 表加 `searchable` 列（检索域隔离，RepDB 摄取时置 false，动作库页走 exercises 表不受影响）；`_fetch_rows` 里 `SET LOCAL hnsw.iterative_scan = strict_order` 让索引按需续扫。验证：污染查询前 5 回到教材页；反事实实验（NASM 也移出检索域）Recall@5 = 0.781 ✅ 过门槛，证明剩余 0.531 纯属"金标准（四大证）vs 本地语料（多 722 块 NASM）"契约错配，检索本身健康。
- **预防**：**任何语料入库都必须回答"进不进检索域"**——参考数据（动作卡/词表/清单）默认不进 RAG 语料；金标准与语料状态是绑定契约，本地评测长期红而 CI 绿 = 语料漂移的烟雾报警器；带过滤条件的向量检索一律开 iterative_scan（或按过滤比例抬 ef_search）。
